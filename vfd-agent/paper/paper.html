Verified, Fast, Deep? A Reasoning LLM, a Zero-Shot Classifier and Tabular Foundation Models in One Data-Analyst Agent

Yarin Benizri
Hebrew University of Jerusalem · open models only, on a Slurm cluster with H200 GPUs · code: excel_magic/vfd-agent · draft, 3 October 2026 · companion papers: Open TabFM-Auto, Which Layer Is the Embedding?
Abstract. Company data-analyst agents are usually one reasoning LLM with SQL tools. We ask whether two other kinds of open model can make such an agent better: a small zero-shot classifier (GLiClass) that checks the agent's steps quickly, and frozen tabular and relational foundation models (Kumo Tabular, Kumo Relational, TabPFN) that read all the rows, not only the rows that fit in the prompt. We give each model one job: the LLM plans and writes SQL, the classifier verifies (“verified, fast”), and the tabular models predict and explain (“deep”). We test this on five benchmarks with open models only. (1) As a verifier of SQL candidates on BIRD, zero-shot GLiClass reaches AUROC 0.685 at 5 ms per candidate, better than the generator's own signals and self-consistency (0.651) but below an LLM judge (0.786, 12× slower); added to the free signals it lifts a stacked verifier from 0.676 to 0.725. It is also the best of five schema linkers. (2) End to end, these gains do not turn into accuracy: no small-model configuration beats plain self-consistency (0.705 vs 0.693 greedy), and schema linking costs -0.026. (3) A guarded auto-research loop rejected 12 of 13 proposed changes; the one it kept raised held-out accuracy from 0.680 to 0.720 (se 0.018). (4) The tabular models add a capability the LLM does not have: on 7 RelBench prediction questions, giving the agent Kumo Relational and Kumo Tabular as tools raises mean AUROC from 0.568 (SQL only) to 0.759. (5) On InsightBench, which scores descriptive insights by recall, the extra tools and the verified insight ledger lower the score (0.304 → 0.230). The models help where their job is the bottleneck, and cost steps where it is not.

1. Introduction

A “BI analyst” agent answers business questions over company databases. The usual design is one large reasoning LLM that reads the schema, writes SQL, reads the result and writes an answer. This design has three known limits. It is hard to know when an answer is wrong. Checking with a second LLM is slow and costly. And the LLM sees only what fits in its prompt: it can count and average, but it cannot fit a model on a million rows to say what drives an outcome or who will churn.

Two kinds of small, open models address these limits on paper. Zero-shot classifiers such as GLiNER and GLiClass score any text against any label in a few milliseconds; they could check each step of the agent. Tabular foundation models (TabPFN, Kumo Tabular) and relational ones (Kumo Relational) predict on new tables with no training; they could give the agent a view of all the data. We ask whether this works in practice, and where.

Contributions. (i) An open system that gives each model one job (Section 3), as a pipeline harness for SQL, as an analyst tool loop, and as a tool server that any coding agent (here pi) can call. (ii) A verifier study: how well a zero-shot classifier tells correct SQL from wrong SQL, against free signals, an NLI model and an LLM judge, and how well it links questions to columns. (iii) End-to-end ablations on BIRD, InsightBench and RelBench, and a text-feature study on 18 tables with text. (iv) A guarded auto-research loop that tunes the harness without overfitting. (v) Negative results, reported as such.

2. Related work

Text-to-SQL. BIRD (Li et al., 2023) is the standard benchmark; many of its gold queries are wrong, and we use the 498-question mini-dev set with the Arcwise-Plat corrections. Strong systems sample many candidates and pick one, by self-consistency (Wang et al., 2023) or by a trained or LLM selector; schema linking (e.g. CHESS, Talaei et al., 2024) shortens the prompt.

Small zero-shot models. GLiNER (Zaratiana et al., 2024) extracts entities of any type with a small bidirectional encoder; GLiClass applies the same idea to classification. NLI cross-encoders are an older zero-shot classifier. LLM-as-judge (Zheng et al., 2023) is the strong but slow verifier.

Tabular and relational foundation models. TabPFN (Hollmann et al., 2025) predicts in context on small tables; Kumo Tabular S/L read larger contexts; relational models such as KumoRFM (Fey et al., 2025) and Kumo Relational predict over a database graph. RelBench (Robinson et al., 2024) gives prediction tasks over real databases with official splits.

Analyst agents and auto-research. InsightBench (Sahu et al., 2025) scores the insights an agent finds in a table against planted ones. Auto-research loops (Karpathy, 2026) let an LLM propose and test changes to a system; our loop adds the overfitting guards of our companion paper Open TabFM-Auto.

3. System

Roles. The reasoning LLM plans, writes SQL and writes the answer. The zero-shot classifier (GLiClass large v3, zero-shot, no fine-tuning) does three cheap jobs: it links a question to schema columns, it scores a (question, SQL, result) triple against hypotheses such as “the query answers the question” and an error taxonomy, and it labels free-text columns. The tabular and relational models run behind a DEEP tool with seven operations: predict, drivers (permutation importance), what-if (partial dependence), anomalies (out-of-fold surprise), drift (two-sample classifier), similar entities and a hypothesis test (paired repeated splits). Each DEEP answer is checked against a gradient-boosting model when the data are large or temporal.

SQL harness. A fixed pipeline: link (top-k columns plus keys) → write → triage (if the classifier's score is below a threshold, one revision with the predicted error labels) → execute → verify (greedy, self-consistency, a stacked logistic regression of cheap signals, or a cascade that sends the uncertain band to an LLM judge). Configurations A–F add one stage at a time (Table 1).

Analyst loop. An OpenAI-style tool loop over DuckDB. D has sql and record_insight; E adds the DEEP tools; F adds text_labels and a verified ledger: an insight is accepted only if its evidence SQL runs again, every number in the sentence appears in that result (with rounding and ratio rules), and GLiClass finds the sentence entailed by the result.

Prediction questions. For RelBench, the agent gets the database cut at the test time, a train_labels and a test_rows table, and must submit a score per test row. D has SQL only; E adds deep_fit_predict (Kumo Tabular-L on features the agent writes in SQL); R adds relational_predict (Kumo Relational's graph layer with a linear probe, the best layer found in our companion paper); ER has both.

Other harnesses. The same tools run as a local HTTP service with a vfd <tool> shell command, so the pi coding agent (used with GLM at the author's company) can call them unchanged.

4. Setup

Models. All open. Generator and analyst: Qwen3-Coder-30B-A3B-Instruct (vLLM). Judge and auto-research researcher: GLM-4.5-Air-FP8, a different model family, thinking off. GLiClass large v3.0; NLI: DeBERTa-v3-large zero-shot v2.0; linkers: bge-small, bge-reranker-v2-m3, GLiNER bi-base v2.0, lexical overlap. Tabular: Kumo Tabular-L and S, TabPFN-2.5, LightGBM; relational: Kumo Relational. One H200 per job.

Benchmarks. BIRD mini-dev with the Arcwise-Plat corrections (498 questions; BIRD set-equality of results). AutoGluon multimodal text+tabular benchmark (Shi et al., 2021), 18 datasets, official splits (train ≤ 3,000, test ≤ 2,000 rows). InsightBench, 100 tables, scored by an open judge (GLM-4.5-Air, G-Eval-style best match per planted insight) and ROUGE-1. RelBench, 8 entity classification tasks, official evaluator. Every comparison is paired over the same questions, tables or tasks; we report the standard error of the paired difference.

Table 2 asks one question per signal: does a higher score mean a correct candidate? Signals that come for free are weak: whether the query runs (0.556) and the generator's log-probability (0.579); self-consistency is better (0.651). Zero-shot GLiClass, with no training on SQL, reaches 0.685 at 5 ms per candidate, above the NLI cross-encoder (0.656). The LLM judge is best (0.786) but 12× slower per call. The signals are complementary: GLiClass lifts the stack of free signals from 0.676 to 0.725; adding the judge gives 0.791.

The catch is in the last column. Picking the best of 9 candidates moves accuracy only from 0.692 to at most 0.746 (the oracle), and no verifier gets close to the oracle: on a corrected benchmark with a strong generator, most questions are either always right or always wrong.

Table 4 puts the stages together. Linking halves the prompt (4,994 → 2,254 characters) but loses accuracy (-0.026, se 0.016): even the best linker leaves out at least one needed column in 38% of questions, and one missing column breaks the query. Triage wins back one point. With 8 candidates, the stacked verifier (D, 0.705) and the judge cascade (F, 0.703) only match plain self-consistency (SC, 0.705), which needs no extra model. The verifier ranks well (Section 5.1), but here there is little to rank.

The researcher LLM proposed one change at a time from a fixed space (linker, top k, triage and its threshold, number of candidates, verifier). Of 13 changes, it kept 1: triage=True. On the held-out questions, scored once at the end, accuracy went from 0.680 to 0.720 (paired +0.040, se 0.018). The guards did their job: three rejected changes had an accept-slice gain of +0.027 and would have been kept by a loop that looked only at one split. Two changes that do nothing (top k with linking off) still moved the search score by up to 0.007, because vLLM greedy decoding is not bit-exact under batching; this is the noise floor any such loop must beat. The kept change is small and depends on the rest of the configuration: in Table 4, triage with linking on was below A.

When a table has text columns, the LLM can propose label sets and GLiClass can turn each text into label scores, which a tabular model reads as features. Table 6 shows that labels help every model on most datasets, but less than a dense sentence embedding. They are complementary: labels plus embedding beat the embedding alone on 15 of 18 datasets for Kumo Tabular-L and 18 of 18 for LightGBM. Labels have one extra value the table does not show: they are readable (“mentions a refund”), so the agent can talk about them.

InsightBench is a negative result for our design. Its planted insights are descriptive (counts, shares and trends on tables of about 500 rows) and its score rewards recall. The DEEP tools (E, 0.266) cost steps without adding descriptive insights, and the verified ledger (F, 0.230) rejects about 2.5 insights per table that the agent does not replace. Verification trades recall for precision, and this benchmark measures only recall.

6. Discussion: where each model helps

  • The zero-shot classifier is a good, fast signal: the best cheap verifier and the best schema linker we tested, at milliseconds per call. A good signal is not the same as a better answer: on BIRD the headroom for selection is small, and linking that drops one column breaks the query. It pays where checking is the bottleneck, for example to flag answers for a human, or with a weaker generator.
  • The tabular and relational models give the agent a new capability, not a small gain: predictions over all rows of a database, from 0.568 to 0.759 AUROC. This is the clearest win in this paper, and the one an LLM-only agent cannot reach by writing better SQL.
  • Verification costs recall. The verified ledger rejects unsupported numbers, which a company report needs, but a benchmark that only counts recall punishes it.
  • Tune with guards. An auto-research loop finds small, real gains only if it is held to a fixed held-out set and a noise floor.

7. Limitations

One generator (Qwen3-Coder-30B) and one judge model; a weaker generator, or the much larger GLM model used in production, may change the verifier results. The BIRD mirrors have no column descriptions. InsightBench is scored by an open judge, not the GPT-4o judge of its paper, so our absolute scores are not comparable to published ones; the paired differences are. RelBench results are 2 episodes per cell; vLLM decoding is not bit-exact, so single runs move by about one point. The pi harness was run once.

8. Conclusion

A reasoning LLM, a zero-shot classifier and tabular foundation models can work as one analyst agent, each with one job. The classifier is a fast and useful verifier signal, but on a strong text-to-SQL setup it does not beat self-consistency. The tabular and relational models are the real extension: they let the agent answer prediction questions over whole databases that SQL alone answers near chance.
